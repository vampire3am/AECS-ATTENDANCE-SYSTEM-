# Architecture

AECS Attend is a modular monolith. `app/` holds role layouts, authentication routes, report exports and thin routing. `features/admin/pages/` contains focused management screens. `lib/services/` owns scheduling, attendance, enrollment and reporting logic. `app/actions.ts` is the authenticated mutation boundary. Every mutation validates its payload and loads current staff permissions from PostgreSQL.

Authentication uses the current stable Auth.js v4 credentials provider. Argon2id hashes use 19 MiB memory, two iterations and one lane. Eight-hour encrypted JWT sessions carry a staff ID and session version; sensitive operations re-read active status and role. Staff edits/password resets increment the version. A shared PostgreSQL counter limits attempts per normalized, HMAC-hashed email to ten per fifteen-minute window. Auth.js handles credential CSRF and secure production cookies. There is no public registration. `AUTH_URL` maps to v4's `NEXTAUTH_URL`; Vercel preview URLs use the platform's auto-detection when no fixed URL is set.

Courses contain batches, batches contain weekly schedules and dated sessions, and students join batches through dated enrollments. Each enrollment includes a course ID constrained to its batch. A student may attend different courses, with only one active enrollment per course. End dates are exclusive for enrollment membership. Transfers close the old row and create a new row in one transaction; they never move historical attendance.

On-demand scheduling uses Asia/Kathmandu's date and ISO weekday. Opening today's session locks the session and verifies the batch assignment, then inserts the dated enrollment snapshot. The roster is sealed before commit. Draft writes and submission lock the same session. Submission validates an exact, complete roster, checks the expected version and atomically finalizes all marks and submission metadata. A unique operation ID makes retries of the same finalized submission idempotent. A competing operation receives a conflict.

PostgreSQL triggers guard session transitions, roster identity, finalized records and audited corrections. An admin correction requires a reason, records the previous/new status and actor, and never rewrites the original audit history. Cancelled/submitted sessions cannot be reopened by ordinary application operations. Audit rows cannot be updated, deleted or truncated by the runtime role.

Reports use submitted sessions only. Present plus optionally late is the numerator; all marked statuses except excused form the denominator. A zero denominator produces no percentage. Reports support date/course/batch/teacher filters and Excel/PDF export. Dates are local class dates, and event timestamps are timezone-aware.

IndexedDB stores actor-scoped rosters, draft versions, operation IDs and synchronization states. Reconnection attempts synchronize drafts but never finalize them. Conflicts preserve the local draft, offer export and explicitly archive it before accepting a server copy. Signing out clears the active offline identity without deleting unsynchronized work. Use offline storage only on trusted devices. The service worker caches static application assets and a dedicated offline shell, not authenticated HTML, auth endpoints or report responses.

Student classroom check-in uses a private random enrollment code and an unpredictable two-minute session token, stored only as a hash. Public POST /api/check-in validates today’s open session, active student/course/batch, dated enrollment and sealed roster, then inserts one pending student_checkins row. Attendance is unchanged until an assigned staff member confirms physical presence. Confirmation is audited and increments the session version. Staff-only polling shows requests. Expired/replaced QR tokens, wrong-batch codes and finalized classes reject submissions. There is no SMS OTP integration; enrollment codes plus teacher verification form the implemented identity/presence workflow.

The public student landing page is available at /student and at / for unauthenticated visitors. A code verification endpoint reveals only student name/ID and course/batch labels after successful private-code validation. It does not expose contact details or authorize attendance by itself. After verification, students use the in-app camera QR scanner, upload a QR image or paste a classroom link. Scans are constrained to same-origin AECS classroom URLs. The camera starts only after a user action, uses the rear camera where supported and stops on completion/unmount. Decoding happens locally. /check-in still supports QR links opened by a phone camera.

Institute-wide permanent QR points to /check-in without credentials or batch IDs. Code-only submissions derive an active enrollment's batch on the server, resolve exactly one open session on the Nepal date, then revalidate active enrollment and sealed roster under the session lock. Pending requests remain duplicate-safe and require assigned staff confirmation. Current/future batches need no QR provisioning or schema change. Legacy token-based session QR links remain supported.

Simplified workflows live in lib/services/workflows.ts. Batch/course/teacher/timetable creation and student/enrollment creation each use one authorized transaction. Start class serializes on the batch, resumes its open session or creates/opens the selected scheduled slot atomically; extra classes require explicit times. Existing finalized-session, roster and private-code invariants remain. Today uses one summary SQL query; admin form options load on demand when Create batch is opened, without session generation or analytics. React cache deduplicates auth reads only within a server render; mutation authorization remains fresh. Catalog projections are selected per page, and analytics charts load only when used. Segment loading boundaries stream a branded skeleton immediately.

Teacher workspaces use separate course-creation grants and batch assignments. Admin-only course grant changes are audited and database-guarded; existing teacher batch assignments backfill course grants. Teacher batch creation revalidates the course grant inside actorTransaction and automatically assigns the new batch to its creator. Assigned batch authorization protects student creation, enrollment/transfer/end, batch edits, schedules, sessions and private-code reads. Scoped report SQL applies the assignment predicate to both ranked attendance and final enrollment results, including exports. Staff creation, course creation, permission changes and global student-profile edits remain admin-only. The student landing is mobile-first with code → class → teacher-check progress and no persisted enrollment code. Staff authentication normalizes email and uses atomic shared account/network counters; parameterized SQL and Zod validation remain mandatory.
